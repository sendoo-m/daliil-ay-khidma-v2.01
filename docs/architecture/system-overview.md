# النظرة المعمارية للنظام

## الهدف

يوثق هذا الملف الحدود الرئيسية للنظام كما هي موجودة حاليًا. لا يمثل هذا الملف وعدًا بأن كل جزء جاهز للإنتاج.

## المكونات

```text
Flutter User App
    |
    | HTTPS / JSON / JWT
    v
Django REST API
    |
    +--> PostgreSQL
    +--> Cloudinary (production media, when configured)
    +--> Firebase Admin / FCM

Django Admin & server-rendered views
    |
    v
Same Django domain and database
```

## Backend

Django هو المصدر الرئيسي للبيانات وقواعد العمل. يتضمن نطاقات للحسابات والدليل والمنتجات والخدمات والعروض والتقييمات والمفضلة والبحث والإشعارات والاشتراكات ولوحات التحكم.

المسؤوليات الأساسية:

- المصادقة وإصدار JWT.
- التحقق من الصلاحيات وملكية الموارد.
- إدارة البيانات والعلاقات.
- البحث والتصفية والترتيب.
- إدارة الوسائط وروابط الصور.
- إرسال وإدارة الإشعارات.
- توفير OpenAPI عند اكتمال التوثيق.

## تطبيق Flutter

تطبيق المستخدم هو عميل API مستقل.

المكونات التقنية الحالية:

- Riverpod لإدارة الحالة والاعتماديات.
- Dio للاتصال بالشبكة.
- Flutter Secure Storage للجلسة والرموز.
- MapLibre للخرائط.
- Geolocator للموقع.
- Firebase Messaging للإشعارات.
- App Links للروابط العميقة.

يجب ألا يحتوي التطبيق على قواعد صلاحيات يعتمد عليها الأمان؛ الـBackend هو جهة الإنفاذ النهائية.

## البيانات الأساسية

العلاقات العامة المتوقعة:

```text
User
  ├── Profile
  ├── Favorites
  ├── Reviews
  └── Devices / Notifications

Location
  Governorate -> City -> District

Category
  └── Business
        ├── Business Images
        ├── Opening Hours
        ├── Products / Services
        ├── Deals
        └── Reviews
```

هذه خريطة مفاهيمية وليست ERD نهائيًا. يجب استخراج نموذج قاعدة البيانات الفعلي في مرحلة الجرد.

## المصادقة

المسار الحالي يعتمد على JWT:

1. المستخدم يسجل أو يدخل.
2. التطبيق يستقبل رموز الجلسة.
3. الرموز الحساسة تحفظ في Secure Storage.
4. Dio يضيف رمز الوصول للطلبات المحمية.
5. الـBackend يتحقق من المستخدم والصلاحية وملكية المورد.

يجب تدقيق تجديد الرمز، تسجيل الخروج، انتهاء الجلسة، وإلغاء الجلسات.

## البحث

البحث يجمع بين الأنشطة والمنتجات والخدمات، مع فلاتر مرتبطة بالموقع والتصنيف والسعر. يجب توثيق عقد موحد للنتائج حتى لا يعتمد Flutter على أشكال استجابة متباينة.

## الوسائط

- التطوير المحلي قد يستخدم تخزينًا محليًا.
- الإنتاج يمكن أن يستخدم Cloudinary عند وجود `CLOUDINARY_URL`.
- يجب أن يعيد API روابط صالحة ومطلقة لكل عميل.
- يجب التحقق من النوع والحجم والأبعاد وسياسة الحذف.

## النشر

### Backend

Render يشغل Django عبر Gunicorn. قاعدة البيانات الإنتاجية يفترض أن تكون PostgreSQL. الاستيقاظ البارد في الخطط منخفضة الموارد يجب التعامل معه كتجربة تشغيل، لا كخطأ تطبيق دائم.

### Flutter

GitHub Actions يقوم حاليًا بـ:

- إنشاء/تجهيز المشاريع الأصلية.
- توليد الترجمة.
- التنسيق والتحليل والاختبارات.
- بناء Web وAndroid.
- بناء iOS بدون توقيع.
- نشر Web على GitHub Pages عند الدفع إلى `master`.

## مخاطر معمارية قيد المراجعة

1. اتساع نطاق كيان النشاط واختلاف أنواع مقدمي الخدمة.
2. احتمال تداخل business وprovider وcreator ككيانات منفصلة.
3. توليد مشاريع Flutter الأصلية داخل CI بدل تثبيت إعداداتها كاملة.
4. اتساق عقود API بين النطاقات.
5. الصلاحيات وملكية الموارد في endpoints المحمية.
6. أداء البحث والاستعلامات مع نمو البيانات.
7. الفصل المستقبلي بين تطبيق المستخدم وتطبيق الإدارة.

## القرارات القادمة المطلوبة

- تعريف Domain Model موحد لمقدم الخدمة.
- اعتماد عقد أخطاء واستجابات API.
- اعتماد استراتيجية البيئات والإعدادات.
- تحديد ما إذا كانت المشاريع الأصلية لـFlutter تحفظ بالكامل في Git.
- تحديد نطاق MVP النهائي قبل بناء تطبيق الإدارة.

كل قرار معماري مؤثر يسجل في `docs/adr/`.
